# Citation-key update validation

This describes the unreleased 5.1.0 development workflow. It does not replace the historical 5.0.71 installed-runtime report.

## Automated evidence

Run `npm test` and `npm run check`.

`tests/key-update.test.js` executes the application update, BibTeX export service, coordinated file writes and database service together. Each fixture has real temporary UTF-8 bibliography/LyX files and a separate SQLite database. Only the Zotero translator and LyX process are simulated.

Covered behavior:

- two documents sharing one bibliography, with an unrelated document and bibliography left intact;
- complete export, verified backups of all modified files, and mapping commit after file verification;
- cyclic keys, prefix-overlapping keys, literal replacement characters and external citations;
- Unicode paths/text, UTF-8 BOMs and mixed document line endings;
- cancellation before changes, unavailable Zotero items and translator failure;
- missing documents, refused saves and acknowledged but canceled closes;
- corrupt/failed backups, partial write failure and SQLite commit rollback;
- incomplete file restoration, retained recovery backups and exact failed paths;
- unsaved edits saved before backup, and external changes detected before a write;
- shared identifiers imported only at successful commit, and ambiguous/reordered headers rejected;
- metadata-only updates without closing or rewriting LyX documents;
- reopening failure after commit reported without undoing a successful update;
- matching message variables in English, German and Hungarian.

`tests/lyx-server.test.js` uses XPCOM stream fixtures for both transport paths. It covers acknowledged commands, explicit errors, foreign-client responses, UTF-8 command bytes, short writes and command queue serialization.

The file writer uses Mozilla's [IOUtils temporary-path write option](https://searchfox.org/mozilla-central/source/dom/chrome-webidl/IOUtils.webidl). The command checks follow the [LyXServer INFO/ERROR protocol](https://wiki.lyx.org/LyX/LyXServer) and use the documented [`buffer-write force` argument](https://raw.githubusercontent.com/cburschka/lyx/master/src/LyXAction.cpp).

## Pending installed-runtime checks

Use an isolated Zotero profile or test library, temporary copies of LyX documents, and a bibliography generated by LyZ. Increment the extension version before reinstalling changed code, as described in CONTRIBUTING.md. Do not force failures against a real writing project.

1. Associate a master and child document with the same bibliography. Add a separate document using another bibliography.
2. Open both associated documents and make an unsaved edit in each. Change a temporary Zotero item's title/author to force a generated key change.
3. Run Update BibTeX and accept the rewrite. Verify both citation insets, `.bib` entries, committed mappings, unique byte-correct backups and preserved unsaved edits. Check that the original active document is selected last.
4. Repeat while one associated document is closed. Check that it is also updated and reopened.
5. Cancel the rewrite confirmation. Verify that bibliography bytes, document bytes and mappings are unchanged.
6. Delete a copied child document and repeat. Verify the exact path is reported and the bibliography/mappings remain unchanged.
7. Use a read-only copied document or directory. Verify save/close/write failures do not commit new mappings; check recovery messages and retained backups.
8. Repeat with an already-saved (clean) buffer, Unicode paths and citations from another bibliography.
9. Check the same lifecycle on Windows, macOS and Linux, including multiple LyX windows on the same process/pipe. Confirm `buffer-close` removes every view of each affected buffer before the file rewrite.

## Recovery boundary

Caught failures before the mapping commit trigger file rollback. A failed rollback leaves old database mappings, reports the incomplete restores, and retains each verified backup under its transaction UUID. Restore the affected bibliography and document files from that UUID's backups as a coherent set after closing them in LyX; keep the backups until the project is checked.

This is a coordinated, recoverable update, not an atomic transaction spanning SQLite and the filesystem. Process termination or power loss between writes and the database commit needs a persistent recovery journal and startup reconciliation in a subsequent change. Native pipe I/O can still block outside the response-polling timeout. Installed-runtime behavior and multiple-window safety remain unverified.
