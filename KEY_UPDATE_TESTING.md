# Citation-key update validation

This describes the unreleased 5.1.0 development workflow. It does not replace the historical 5.0.71 installed-runtime report.

## Automated evidence

Run `npm test` and `npm run check`.

`tests/key-update.test.js` executes the application update, BibTeX export service, coordinated file writes and database service together. Each fixture has real temporary UTF-8 bibliography/LyX files and a separate SQLite database. Only the Zotero translator and LyX process are simulated.

Covered behavior:

- two documents sharing one bibliography, with an unrelated document and bibliography left intact;
- complete export, verified backups of all modified files, and mapping commit after file verification;
- cyclic keys, prefix-overlapping keys, literal replacement characters and external citations;
- Unicode paths/text, UTF-8 BOMs and mixed document line endings;
- cancellation before changes, unavailable Zotero items and translator failure;
- missing documents, refused saves and acknowledged but canceled closes;
- corrupt/failed backups, partial write failure and SQLite commit rollback;
- incomplete file restoration, retained recovery backups and exact failed paths;
- unsaved edits saved before backup, and external changes detected before a write;
- shared identifiers imported only at successful commit, and ambiguous/reordered headers rejected;
- metadata-only updates without closing or rewriting LyX documents;
- reopening failure after commit reported without undoing a successful update;
- matching message variables in English, German and Hungarian.

`tests/lyx-server.test.js` runs the production worker's protocol loop with a native-I/O adapter and tests the UI worker controller. It covers acknowledged commands, explicit errors, foreign-client responses, split UTF-8/complete-line handling, short writes, input validation, worker stalls, output reconnection without a resend, endpoint cleanup and command queue recovery. Session identifiers are also checked across restarted service instances.

`tests/key-recovery.test.js` launches a separate Node.js process and terminates it without running rollback or cleanup. A fresh process/connection then checks the persisted files and SQLite state. Exit checkpoints cover journal preparation, incomplete temporary-file staging, each of three file replacements, an uncommitted mapping transaction and the completed SQLite commit. Tests also cover declined recovery, external edits before/during recovery, damaged backups, retry after a failed restore, malformed/unsupported journals, changed mappings, a rejected promise after durable commit, journal-cleanup errors and shared startup initialization.

The database-audit and diagnostic-export regression suite is described in [DATABASE_RECOVERY.md](DATABASE_RECOVERY.md).

Current local evidence (2026-09-27, Windows, Node.js 26): 126 tests passed; add-on JavaScript syntax and XPI integrity/source-content checks passed. The Node fixtures simulate Zotero translation and native XPCOM hashing/pipe I/O. Separate installed Zotero 10.0.1 / LyX 2.5.3 tests pass 31 checks using real translation, hashing, SQLite and native Windows named pipes; see [ZOTERO_LYX_RUNTIME_TEST.md](ZOTERO_LYX_RUNTIME_TEST.md). Mapping-manager coverage is documented in [MAPPING_MANAGER.md](MAPPING_MANAGER.md).

Windows filesystem paths received from LyX are converted to native separators only at the `IOUtils`/`PathUtils` boundary, including backup and temporary-write paths. Stored mappings, journals and LyX commands retain their paths. Existing buffers are selected with `buffer-switch`; an explicit server ERROR permits `file-open` for a closed document. Transport failures abort without attempting that fallback. Regression tests cover these native-runtime defects.

The file writer uses Mozilla's [IOUtils temporary-path write option](https://searchfox.org/mozilla-central/source/dom/chrome-webidl/IOUtils.webidl). The command checks follow the [LyXServer INFO/ERROR protocol](https://wiki.lyx.org/LyX/LyXServer) and use the documented [`buffer-write force` argument](https://raw.githubusercontent.com/cburschka/lyx/master/src/LyXAction.cpp).

## Pending installed-runtime checks

The automated Windows lifecycle covers the shared-bibliography, unsaved-edit, successful rewrite/backup, closed-document, cancellation, Unicode and prepared-journal restart cases below. It uses two separate associated documents rather than a LyX parent/child include relationship, and injects dialog answers instead of exercising interactive confirmations. Keep the following checklist for manual review, additional failure cases and other platforms/windows.

Use an isolated Zotero profile or test library, temporary copies of LyX documents, and a bibliography generated by LyZ. Increment the extension version before reinstalling changed code, as described in CONTRIBUTING.md. Do not force failures against a real writing project.

1. Associate a master and child document with the same bibliography. Add a separate document using another bibliography.
2. Open both associated documents and make an unsaved edit in each. Change a temporary Zotero item's title/author to force a generated key change.
3. Run Update BibTeX and accept the rewrite. Verify both citation insets, `.bib` entries, committed mappings, unique byte-correct backups and preserved unsaved edits. Check that the original active document is selected last.
4. Repeat while one associated document is closed. Check that it is also updated and reopened.
5. Cancel the rewrite confirmation. Verify that bibliography bytes, document bytes and mappings are unchanged.
6. Delete a copied child document and repeat. Verify the exact path is reported and the bibliography/mappings remain unchanged.
7. Use a read-only copied document or directory. Verify save/close/write failures do not commit new mappings; check recovery messages and retained backups.
8. Repeat with an already-saved (clean) buffer, Unicode paths and citations from another bibliography.
9. Check the same lifecycle on Windows, macOS and Linux, including multiple LyX windows on the same process/pipe. Confirm `buffer-close` removes every view of each affected buffer before the file rewrite.
10. Terminate an isolated Zotero process during a key update and restart it. Close affected LyX documents before accepting the recovery prompt. Verify byte-correct restoration, unchanged old mappings, retained backups and removal of the completed recovery record.
11. Decline restart recovery. Verify citation insertion, updates and mapping management remain blocked while Settings and LyX Command still work. Retry after closing the documents; check that recovery is offered only once per startup attempt.
12. Make an external edit to a copied affected document before restarting. Verify recovery preserves that edit and reports its path instead of overwriting it. Keep all recovery artifacts for diagnosis.

## Recovery boundary

Before the first file replacement, `key_updates` stores a format-versioned journal with the transaction UUID, old/new mappings, file/backup/staging paths and SHA-256 fingerprints of old/new bytes. The new mappings and the `committed` marker are saved in one SQLite transaction. A journal is retired only after successful commit or verified rollback; backups are retained.

At startup, a `prepared` record with unchanged files can be retired without writing. Recognized replacements can be restored from verified backups after the user closes all affected LyX documents and confirms. An already `committed` record is retired only if its files and new mappings still match; it is never rolled back merely because a previous connection reported an error. Recovery rechecks the entire set after confirmation and checks each file again before replacing it. It can resume after another failed restore.

Missing or externally edited files, altered mappings, invalid journals and damaged required backups stop recovery and retain the journal and verified artifacts. Further data-changing menu actions are blocked; Settings, LyX Command and Export database diagnostics remain available. A prepared transaction can be retried once its coherent original state or recognized replacements and valid backups are restored. Do not manually delete the journal or edit SQLite mappings to bypass this check. Diagnostic export is described in [DATABASE_RECOVERY.md](DATABASE_RECOVERY.md); a guided repair/import interface is still pending.

The filesystem and SQLite are coordinated through the journal rather than made atomically transactional together. Process termination is covered by the Node fixtures at multiple checkpoints and by installed Windows Zotero after the first native file replacement. Native XPCOM operations and prepared-journal startup recovery pass in that installed lifecycle. Real device/power-loss durability, other platforms and multiple-window safety remain unverified. The 2026-10-01 transport moves native pipe operations off the UI thread and bounds the entire request; a real silent Windows pipe verifies timeout and UI responsiveness. Native macOS/Linux transport checks remain pending.
